# 送信に至るまでの安全装置

既定の設定では、どこにも何も送信されません。実際に投票を1件送信するには、互いに独立した5つの手順をすべて意図的に行う必要があります。この文書では、それぞれの手順と、外した場合に何が起こりうるかを説明します。

## 5つの条件

**1. 本番ドライバを選ぶ。** 既定は `--driver paper`（模擬投票）で、手元のファイルに記録するだけです。ネットワークに送信するには `--driver live` を明示的に指定する必要があります。launchd に本番用として導入する場合は、導入前に確認の入力も求められます。

**2. ポリシーで送信が有効になっている。** ポリシーファイルの `submission.enabled` に加えて、1レースあたり・1日あたりの上限額、金額の単位、購入できる券種などを定めます。そもそもポリシーは `frozen_for_implementation`（確定済み）の状態でなければ読み込まれません。

**3. ポリシーと計画の日付が一致している。** 生成したポリシーは、ちょうど1日だけ有効です。計画の日付がポリシーの日付と一致し、発走予定時刻がポリシーのタイムゾーンでその日に含まれている必要があります。前日の計画を翌日に送信することはできません。

**4. 日付入りの環境変数がそろっている。** ポリシーが指定する環境変数（例: `KEIBA_ENABLE_SUBMISSION=2026-09-26`）が、指定どおりの値で設定されている必要があります。その日の送信は、その日に誰かが判断して許可するもので、以前に設定したままのものであってはならない、という考えからあえて手間をかけています。

launchd で常駐させる場合は、この条件を明示的に指定する必要があります。`scripts/launchd.sh install --enable-submission` を使うと、ポリシーの指定が設定ファイルに書き写され、何を設定したかが表示されます。指定しなければ、デーモンは起動しても送信を許可できません。何か月も前に導入したデーモンが勝手に送信しないようにするためです。

**5. 運用者が計画のハッシュ値を入力して送信を許可する。** `votectl arm-day --confirm-sha256 <ハッシュ値>` を実行します。入力したハッシュ値は、デーモンが計画ファイルの内容から計算し直した値と一致しなければなりません。計画の内容が1ポイントでも変わっていれば、ここで止まります。

これらとは別に、いつでもすべてを止められる仕組みがあります。

**緊急停止ファイル。** ポリシーが指定する場所（既定は `var/STOP_VOTING`）にファイルがある間は、何も送信されません。ファイルを置くだけで止められ、プロセスを操作する必要はありません。

```bash
touch var/STOP_VOTING                                  # 送信を止める
./bin/votectl --policy <ポリシー> kill --reason "理由"   # 止めて理由を記録する
```

## 意図して設定していただきたい上限

| ポリシーの項目 | 制限する内容 |
|---|---|
| `max_stake_per_race` | 1レースあたりの上限額 |
| `max_daily_total_stake` | 1日あたりの上限額 |
| `max_bets_per_race` | 1レースあたりの点数 |
| `max_races` | 1日のレース数 |
| `max_post_requests` | このポリシーでの送信回数の合計 |
| `allowed_bet_id_patterns` | 購入を認める券種 |
| `stake_unit` | 金額の単位（100に固定） |

計画を取り込む時点で、送信の許可より前に、これらの上限と照合します。上限を超える計画は、一部だけが送信されることはなく、全体が受け付けられません。

## 設定では変えられない動作

**1レースにつき送信は1回だけ。** 再試行の方針ではなく、変更できない決まりです。

**結果が不明な送信は再試行しない。** タイムアウトや通信の切断、解釈できない応答が起きた場合、そのレースは `AMBIGUOUS`（結果不明）となり、その日の以降の送信を止めて人の判断を待ちます。再試行すると同じレースに2回投票してしまうおそれがあり、それは取り消せないためです。

**再起動したとき、送信中だったレースは読み返しだけを行う。** 何が起きたかを大会側に問い合わせるだけで、確かめるための再送信はしません。

**確認は応答コードではなく読み返しで行う。** 大会側に記録された投票を読み返し、送信した内容と項目ごとに比べます。1か所でも違えば `CONFLICT`（不一致）となります。

## 認証情報の扱い

`KEIBA_LOGIN_ID` と `KEIBA_PASSWORD` は環境変数からのみ読み込みます。状態ディレクトリにもログにも書き出さず、launchd の設定ファイルのテンプレートにも含めていません。設定ファイルは他のユーザーからも読め、バックアップにも含まれるためです。macOS のキーチェーンに保存し、起動時に環境変数へ読み込む方法をおすすめします。

模擬投票ドライバは、これらの値を一切使いません。

## 大会終了後について

本番の投票 API は、大会の開催期間中しか投票を受け付けません。2026年の大会は2026年9月22日に終了しました。現在 `--driver live` を使うと、5つの条件をどのように設定しても送信の段階で失敗します。これは大会側の仕様によるものです。

それ以外の機能はすべて動きます。模擬投票ドライバは本番と同じ状態の遷移、台帳、照合の処理を通るので、大会終了後も、このランタイムの動作を確かめたり、これをもとに開発したりすることができます。
