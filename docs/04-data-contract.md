# データ形式

このリポジトリには、レースのデータを一切入れていません。過去のオッズや結果は提供元に権利があり、私から再配布することはできないためです。また、私が大会の準備で集めたデータは数十GBの規模になります。

その代わりに、ここで説明するデータ形式と、同じ形式で「本当の確率がわかっている」合成データを作る生成器を用意しました。

## パネル（レースデータの集まり）

パイプラインが読み込むのは、1レースにつき1つの JSON ファイルが日付ごとのディレクトリに並んだものです。私はこれを「パネル」と呼んでいます。

```
panel/
  20260926/
    202609260411.json
    202609260412.json
```

```json
{
  "race_id": "202609260411",
  "date": "20260926",
  "post_at": "2026-09-26T05:30:00Z",
  "captured_at": "2026-09-26T05:20:00Z",
  "win": {"1": 3.2, "2": 11.4, "3": 26.0},
  "trifecta": {"1-2-3": 320.4, "1-3-2": 455.1},
  "result": {
    "finish": [5, 2, 7],
    "payout_per_100": {"5-2-7": 4321.0}
  }
}
```

| 項目 | 意味 |
|---|---|
| `race_id` | 半角英数字ちょうど12文字。投票ランタイムもこの形式を検査します。 |
| `date` | `YYYYMMDD` 形式の開催日。ディレクトリ名と一致させてください。 |
| `post_at` | 発走予定時刻。タイムゾーンの指定が必要です。 |
| `captured_at` | このオッズを取得した時刻。`post_at` より前である必要があります。 |
| `win` | 馬番ごとの単勝オッズ（`captured_at` 時点）。 |
| `trifecta` | 着順どおりの3頭の組合せごとの三連単オッズ（`captured_at` 時点）。 |
| `result` | 確定した結果。レースが確定するまでは含めません。 |

`payout_per_100` は、100ポイントあたりの公式の払戻額を倍率で表したものです（円の金額ではありません）。新しいデータ源を使う場合は、公式の払戻額と保存した値を1件突き合わせて、単位を確認することをおすすめします。

## 守っていただきたい決まりごと

ここに挙げるのは、正しい検証結果を得るために私が必ず守るようにしていたことです。いくつかはローダーが自動で検査します。

**オッズの取得時刻は発走より前であること。** `captured_at` が `post_at` 以降のファイルは、読み込み時にエラーになります。発走後に取得したオッズを使うと、実際には誰にも下せなかった判断を検証していることになり、結果が不当に良く見えてしまいます。収集処理が再試行した場合などに、気づかないうちに起こりやすい問題です。

**ファイルの更新日時を取得時刻の代わりに使わないこと。** ファイルをコピーしたり同期したりすると、中身は古くても更新日時は新しくなります。

**結果を予測の入力に使わないこと。** `result` はバックテストで払戻を計算するためだけにあります。確率や判断を計算する処理から読まれないよう、ローダーは別の項目として分けて保持しています。特徴量を作る処理が `result` を参照するのは、学習時に的中した組合せの位置を特定するときだけです。

**確定オッズを入力に使わないこと。** 確定オッズは締切後にしかわからない値です。データ源に含まれていても、`win` や `trifecta` には入れないでください。

**「不明」を「外れ」として扱わないこと。** 確定したレースで、ある組合せの払戻が記録されていなければ、その馬券は外れたことを意味し、払戻は `0.0` になります。一方、まだ確定していない、あるいは結果がわからないレースは `None` となり、バックテストでは残高に含めず件数を別に報告します。不明を外れとみなすと結果を低く、的中とみなすと高く見積もってしまうためです。

## 取得が不完全なレース

オッズの一部しか取得できていないレースは、推測で補わずにエラーとして除外し、`train` は除外した件数を報告します。この件数も検証結果の一部として見ていただきたい数字です。多くのレースが除外されている場合、取得に成功したレースだけを選んで評価していることになり、取得が失敗しやすい条件と結果が偏って関係している可能性があります。

## ご自身でデータを用意する場合

上記の形式でファイルを出力する仕組みを用意すれば、そのまま使えます。データの取得にあたっては、次の点にご配慮ください。

- 取得先のサイトやサービスの利用規約をご確認ください。
- `robots.txt` やアクセス頻度の制限を守り、サーバに負担をかけないよう、間隔をあけて取得してください（1秒に1回程度を目安にしてください）。
- 取得に使うプログラムの User-Agent には、どのようなプログラムかがわかる名前を設定してください。
- 取得したオッズの再配布は、多くの場合認められていません。パネルはリポジトリに含めないでください。このリポジトリの `.gitignore` でも `/data` を除外しています。

## 合成データの生成器

```bash
.venv/bin/python -m pykeiba synth --out data/synthetic --days 6 --races-per-day 12 --seed 7
```

この生成器は、検証結果が実際より良く見えてしまわないよう、次のように作りました。

- 市場の確率は、本当の確率に誤差を加えたうえで、控除分を上乗せしてオッズにしています。モデルが見つけられるような優位性は、データの中に含めていません。
- 的中した馬券は、賭けた時点のオッズより低い倍率で払い戻されます（倍率の中央値は0.85倍）。実際のレースでも締切まで賭けが集まり続けるため、確定オッズは賭けた時点のオッズと異なります。これを再現しないと、どの戦略も実際より良く見えてしまいます。配分の計算にある `odds_factor` は、この差を見込むための値です。
- 着順は、各馬の本当の強さに基づいて順に抽選しています（Plackett-Luce モデル）。このため Harville モデルがほぼ正しく当てはまる、Harville にとって最も有利な条件になっています。holdout の結果を読むときは、この点を念頭に置いてください。
