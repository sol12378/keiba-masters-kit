# 投票ランタイム

`votingd` は、1つのポリシー、1つの状態ディレクトリ、1日分のレースを受け持つデーモンです。書き込みを行うのは常にこのプロセス1つだけです。

役割はあえて狭くしています。`votingd` は何も判断しません。起動前に確定してハッシュ値が付けられた計画を受け取り、各レースを1回だけ送信し、大会側に何が記録されたかを確かめる。それだけを行います。

## 判断をデーモンの外で確定させる理由

確率の計算、金額の決定、買う組合せの選択といった判断はすべて Python 側で行い、その結果は内容のハッシュ値を含む計画ファイルとして書き出されます。デーモンはそのハッシュ値を自分で計算し直して確かめ、運用者が同じハッシュ値を入力してその日の送信を許可したときに、はじめて送信できる状態になります。

この分担によって、後から検証できるようになります。「モデルが出した結論」と「実際に送信した内容」のあいだで計画が変わっていないことを、両者が同じハッシュ値を持っていることで確かめられるからです。

## 状態の遷移

```
DISCOVERED ──► VALIDATED ──► ARMED ──► POSTING ──► PENDING_CONFIRMATION ──► CONFIRMED
                   │            │          │                │                  │
                   │            │          │                ├──► CONFIRMED_EXISTING
                   │            │          │                ├──► CONFLICT
                   │            │          │                └──► AMBIGUOUS
                   │            │          └──► REJECTED
                   ├──► EXPIRED └──► KILLED
```

とくに理解しておいていただきたいのは、うまくいかなかった場合の状態です。

- **AMBIGUOUS（結果不明）**: 送信はしたものの、結果がわからない状態です。タイムアウト、通信の切断、解釈できない応答などで起こります。デーモンはこの場合に再送信を行いません。再送すると、すでに投票済みのレースに2回目の投票をしてしまうおそれがあり、1レース1回の投票しか認められない大会では取り返しがつかないためです。その日の以降の送信を止め、人の判断を待ちます。
- **CONFIRMED_EXISTING（既存の投票を確認）**: 読み返したときに、デーモンが送信した記録のない投票が見つかった状態です。ほとんどの場合、プロセスが止まる直前に自分が送信していたものです。この状態があるので、途中で止まっても安全に再開できます。
- **CONFLICT（不一致）**: 読み返した内容が、送信した内容と食い違っている状態です。この場合は処理を止めます。

## 取り込みと送信許可は別の手順

`import-day` は計画ファイルを検証し、各レースを `VALIDATED` として保存します。`arm-day` は、運用者に計画ファイルのハッシュ値の入力を求めたうえで、ファイル内の各レースが取り込み済みの内容と一致するかを確かめます。確かめるのは、送信内容のハッシュ値と、発走時刻などの予定の両方です。

予定も確認しているのは、送信内容のハッシュ値が予定を含んでいないためです。送信内容は「レースID・印・買い目」だけなので、同じ買い目を別の発走時刻で組み直しても、そのハッシュ値は変わらず、計画ファイル全体のハッシュ値だけが変わります。予定を比べなければ、運用者は新しい計画を確認したつもりで、以前に取り込んだ古い予定のまま送信を許可してしまいます。実際に、開発中にこれで4レースが許可と同時に期限切れ（`EXPIRED`）になりました。計画を組み直したときは、取り込みからやり直してください。

## 途中で止まったときの再開

ジャーナル（処理の記録）は追記のみで書かれ、1件ごとにディスクへ確実に書き込まれます。また `POSTING`（送信中）の記録は、通信を行う**前**に書き込まれます。

そのため、プロセスが途中で止まっても、再開したデーモンは「送信が行われたかもしれない」ことを知っています。`POSTING` のまま残っているレースについては、読み返しだけを行い、返ってきた結果をそのまま受け入れます。確かめるために再送信することはありません。

launchd の自動再起動（`KeepAlive`）を安全に使えるのは、この仕組みがあるためです。再起動したデーモンは、自分が意図していたことではなく、実際に起きたことに合わせて状態を整えます。

## 照合

「送信が成功応答を返した」ことを、確認とはみなしません。デーモンは投票内容を大会側から読み返し、手元の送信内容と項目ごとに比べます。既定の設定（`require_exact_get_reconciliation`）では、1か所でも違えば `CONFLICT` になります。

送信前に読み返した結果が空だった場合は「まだ投票がない」と判断しますが、その判断はごく限られた応答の形（HTTP 200、想定どおりの操作、ステータス `NG`、理由の記載なし）に限っています。それ以外の形の応答は、判断できないものとして安全側に倒します（fail-closed）。

## 外部とのやりとり

| | |
|---|---|
| 操作 | 状態ディレクトリ内の Unix ソケット（権限0600）。`votectl` がここを通じて操作します。 |
| 状態の参照 | ループバックアドレス上の読み取り専用 HTTP。ポリシーで許可しない限り、外部からの接続は受け付けません。 |
| ジャーナル | `events.jsonl`。追記のみで、1件ごとに書き込みを確定します。 |
| スナップショット | `snapshot.json`。書き換えはアトミックに行います。 |

操作用のソケットはプロセスの排他制御も兼ねています。同じ状態ディレクトリに対して2つ目のデーモンは起動できないため、書き込みを行うプロセスが2つになることはありません。

## ドライバ

```go
type API interface {
	Login(context.Context, string, string) (string, error)
	Check(context.Context, string, string) ([]CheckedVote, error)
	Submit(context.Context, string, RacePayload) (SubmitReceipt, error)
}
```

実装は2つあります。

**`paper`（模擬投票、既定）** は、投票を模擬の残高とともに手元の JSON ファイルに記録します。本番の API と同じ形の「まだ投票がない」という応答を返すので、ランタイムの安全側の処理が省略されずにそのまま動きます。アカウントもネットワークも不要で、大会期間外でも動くのはこのドライバだけです。認証を行わないので、認証情報も求めません。

**`live`（本番）** は、大会の投票 API に送信します。大会のアカウントが必要で、大会が投票を受け付けている期間しか使えません。2026年の大会は2026年9月22日に終了したため、現在はどのように設定しても送信の段階で失敗します。これは大会側の仕様によるもので、本リポジトリの不具合ではありません。

ドライバは `--driver` で選び、選んだものはデーモンの起動時のログに記録されます。
