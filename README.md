# keiba-masters-kit

AI競馬予想マスターズ2026に参加した際に私が作った投票の仕組みと、投票内容を決めるモデルを公開します。来年以降に参加される方の参考になればと思い、手元で同じように動かせる形に整理しました。

> **ご注意**
>
> - これは私個人による**非公式**の公開物で、大会運営とは関係ありません。
> - 扱うのは大会の仮想ポイントだけで、実際の馬券は購入しません。
> - 日本では勝馬投票券の購入は20歳以上に限られています。お使いになる前に [DISCLAIMER.md](DISCLAIMER.md) をお読みください。

English: [README.en.md](README.en.md)

## 概要

このリポジトリは、次の2つの部分と、それらをつなぐ「計画ファイル」でできています。

- **投票ランタイム（Go）**: 1日分の確定した計画を受け取り、各レースの発走前に1回だけ送信し、大会側のサーバに記録された内容を読み返して照合します。処理の記録は追記だけで残すので、送信の途中でプロセスが止まっても安全に再開できます。macOS の launchd で常駐させて使っていました。
- **モデル構築パイプライン（Python）**: 判断時点のオッズから計画ファイルを作ります。控除分を除いた市場確率、単勝オッズから求める Harville の順序確率、その2つを組み合わせる小さな対数線形モデル、そして「残りレース数と所持ポイントに応じて、どの価格帯にいくら賭けるか」を決める動的計画法で構成しています。

判断（Python）と送信（Go）を分けたのは、あとから「モデルが出した結論」と「実際に送った内容」が同じだったことを確かめられるようにしたかったからです。計画ファイルには内容のハッシュ値（SHA-256）を付け、Go 側と Python 側がそれぞれ同じ値を計算して照合しています。両者が一致することはテストでも確かめているので、形式の食い違いはレース当日ではなく開発中に見つかります。

## 限界と注意点

先にお伝えしておくと、このリポジトリは市場に勝つ方法を示すものではありません。

- モデルの入力は市場から得られる2つの値だけで、既定では市場確率に5%だけ混ぜて使っています。同梱の合成データで検証すると、予測精度の改善（holdout の NLL）は 5.8 のうち約 0.015 と、ごくわずかです。
- 動的計画法は、どの価格帯も払戻率が100%を下回る（平均すると損をする）ことを前提にしています。私がこれで決めていたのは「いつリスクを取るか」であって、期待値を上げる方法ではありません。
- 求めた到達確率は、理論上の上限 `P(到達) ≤ 最大払戻率 × 初期資金 ÷ 目標` と照合しています。これを超える結果が出た場合は、計算の誤りとみなして処理を止めるようにしました。

`make model` を実行すると、検証結果に最終残高の平均（`mean_final_bank`）と中央値（`median_final_bank`）が表示されます。平均は初期資金を下回り、中央値は既定の設定ではほぼゼロになります。目標に届く可能性と引き換えに、多くの場合は資金の大半を失う、というのがこの手法の実際の姿です。

大会では良い結果になりましたが、的中は204レース中4回でした。運による部分が大きかったと考えています。

## 動作環境

macOS（Apple silicon / Intel）、Go 1.26 以降、Python 3.11 以降、[uv](https://github.com/astral-sh/uv) が必要です。

Go と Python の部分は他の OS でも動くはずですが、私は macOS の launchd で常駐させていたので、Linux（systemd）や Windows 向けの手順は用意していません。

## はじめかた

```bash
make setup
make model
make demo
```

- `make model` は、データの用意もネットワーク接続も要りません。合成データの生成、学習、方策表の計算、シミュレーションによる検証、バックテストまでを順に実行します。
- `make demo` は、投票の流れ全体を手元で再現します。レースの発走時刻を数分後に付け替えて計画を作り、模擬投票ドライバで `votingd` を起動して送信を許可すると、各レースが時刻どおりに送信・照合されます。アカウントや認証情報は要りません。

詳しい手順は [docs/01-quickstart.md](docs/01-quickstart.md) に書きました。

## 大会への送信について

本番ドライバ（`--driver live`）は、環境変数 `KEIBA_LOGIN_ID` と `KEIBA_PASSWORD` に設定したご自身のアカウントで、大会の投票 API に送信します。大会期間中、私はこのドライバで実際に投票していました。

本番ドライバは、大会が投票を受け付けている期間しか使えません。2026年の大会は2026年9月22日に終了しているため、現在は送信先がありません。大会が終わってからも試していただけるように、既定では模擬投票ドライバを使うようにしています。

実際に送信が行われるのは、次の条件がすべてそろったときだけです。

1. 本番ドライバが選ばれている
2. ポリシーファイルで送信が有効になっている
3. ポリシーの日付と計画の日付が一致している
4. 日付入りの環境変数がポリシーの指定と一致している
5. 運用者が計画のハッシュ値を入力して、その日の送信を許可している

さらに、緊急停止ファイルが置かれている間は何も送信されません。誤って送信することだけは避けたかったので、あえて段階を多くしました。詳しくは [docs/06-safety.md](docs/06-safety.md) をご覧ください。

## データについて

レースのデータ（オッズや結果）は含めていません。これらは提供元に権利があり、私から再配布することはできないためです。

その代わりに、データ形式の説明（[docs/04-data-contract.md](docs/04-data-contract.md)）と、同じ形式の合成データを作る生成器を入れています。ご自身で正当に入手したデータを同じ形式にそろえれば、同じように使えます。

## 大会で実際に使ったコード

`pykeiba/` は、私が大会で使った手法を汎用化して書き直したものです。大会期間中に実際に動かしたスクリプトそのものは [submission/](submission/) に、当時の状態のまま入れてあります。運営への提出物として整理したものです。

- 8/29〜9/19（190レース）の投票方針と、計画を作るまでの処理（このうち方策表を直接参照したのは8/29の29レース）
- 9/20（14レース）の学習コードと確定した係数、およびその係数が再現できることの確認
- 実際に投票した204レースの買い目を含む台帳と、残高の照合結果（まだ照合できていない1,000ptを含む）

公開にあたっては、大会終了後に運営の皆さまへ確認し、ご了承をいただきました。
